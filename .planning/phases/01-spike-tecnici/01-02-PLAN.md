Primitive dell'harness per i piani consumatori (Git Bash sull'host; chiuse dopo questa wave). Tutti i comandi leggono `CKA_SPIKES_ENV` (default `$HOME/.cka-spikes/spikes.env`) e lanciano `docker compose --env-file "$CKA_SPIKES_ENV" -f spikes/compose.yaml`; nessuno stampa valori dell'env.

Unico script di orchestrazione `bash spikes/tools/session.sh <sottocomando>` (firme allineate alla richiesta del piano 01-04; il `run_id` è sempre esplicito):

- **Validazione del run_id** in OGNI sottocomando che riceve o legge un `run_id` (`acquire`, `up`, `run`, `oneshot`, `exec`, `cid`, `stop`, `down`, `release`, `init-volumes`, `ps`, e `reclaim` sul `run_id` letto da `owner`): deve corrispondere a `^[a-z0-9][a-z0-9-]{0,62}$` e non essere `none` (valore di default dell'etichetta, riservato); vuoto o non valido → exit 2 prima di qualsiasi comando docker. Nessun comando costruisce mai un filtro `label=cka.run_id=` con valore vuoto.
- `session.sh new-id <piano>` → stampa un `run_id` = `<piano>-<UTC YYYYMMDDTHHMMSSZ>-<4 hex>` minuscolo (valido come nome DNS).
- `session.sh acquire <piano> <run_id> [--wait <secondi>]` (`run_id` anche scelto dal chiamante, purché valido, altrimenti exit 2): prenotazione atomica della finestra di misura con proprietario (`mkdir` della dir di lock, poi `owner` scritto in un file temporaneo dentro la dir e pubblicato con `mv` atomico); exit 0, oppure exit 3 stampando il proprietario se la prenotazione è di altri, o `IN CREAZIONE` se la dir esiste senza `owner`; una prenotazione stantia (pid proprietario non vivo, oppure `owner` assente da oltre `CKA_LOCK_GRACE_S` secondi, default 30, misurati sull'mtime della dir) viene segnalata come tale, mai sottratta in silenzio (vedi `reclaim`).
- `session.sh up <run_id> <servizio…>`: verifica il set risolto (`config`) = set nominato, rifiuta se un servizio nominato è già in esecuzione con un altro `cka.run_id`, avvia con `compose up -d --no-deps --wait` i soli servizi nominati, senza profili.
- `session.sh run <run_id> <container_name> -- <comando…>`: `compose run -d --no-deps --name <container_name> --label cka.run_id=<run_id> runner <comando…>`; il container è raggiungibile per nome DNS dagli altri container della sessione sulle reti `default` e `parse` (es. `cka-s01-server`).
- `session.sh oneshot <run_id> -- <comando…>`: come `run`, in primo piano con `--rm`; nessuna opzione docker inoltrata (né `--user` né altre): tutto ciò che segue `--` è il comando eseguito nel runner come 10001.
- `session.sh init-volumes <run_id>`: unico passo come root, a firma fissa (argomenti in più → exit 2): `compose run --rm --no-deps --user 0:0 --label cka.run_id=<run_id> runner chown -R 10001:10001 /target /usr/local/cargo/registry /work/tmp`, con i tre percorsi scritti nello script; idempotente. `session.sh exec <run_id> <servizio|container_name> -- <comando…>`: `docker exec` solo se l'etichetta coincide (lettura di `/sys/fs/cgroup/memory.peak`, `/proc/<pid>/status`); un nome di servizio compose (es. `worker`, `paddle`) è risolto con `cid`.
- `session.sh cid <run_id> <servizio>` → stampa l'id dell'unico container del servizio avviato da quel run_id (`docker ps -q --filter label=cka.run_id=<run_id> --filter label=com.docker.compose.service=<servizio>`); exit ≠ 0 se ne trova zero o più di uno. I piani non scrivono mai a mano nomi di container compose (`cka-spikes-<svc>-1`).
- `session.sh stop <run_id> <container>`: ferma e rimuove UN container (nome o id) solo se porta l'etichetta `cka.run_id=<run_id>`, altrimenti rifiuta con exit ≠ 0 senza toccarlo (es. arresto del solo job `cka-s01-server`).
- `session.sh down <run_id>`: ferma e rimuove tutti e soli i container con etichetta docker `cka.run_id=<run_id>`, filtrati per etichetta su tutti i container e non solo sui servizi compose: servizi, job di `run`/`oneshot` e container lanciati fuori compose con `docker run --label cka.run_id=<run_id>` (es. TEI CPU, `gen_hostile`, `cka-gpu-check`); è la pulizia garantita di ogni sessione; mai `docker compose down`, mai volumi.
- `session.sh release <run_id>`: rilascia solo se il `run_id` coincide col proprietario.
- `session.sh with <piano> -- <comando…>`: `new-id` + `acquire` + export `CKA_RUN_ID`, comando, e in uscita (normale, errore, INT/TERM) `down` + `release`. Forma consigliata per una sessione intera.
- `session.sh status`; `session.sh reclaim` (solo con prenotazione stantia: con pid morto, `down` del suo run_id validato, poi rilascio; con `owner` assente oltre la grazia, solo rimozione della dir di lock, nessun `down`; con `owner` assente entro la grazia o proprietario vivo, exit 3 senza toccare nulla); `session.sh ps <run_id> [--assert-only <servizio…>]` (exit 1 se in esecuzione c'è un servizio del progetto fuori elenco, es. TEI in una sessione Docling; i job di `run`/`oneshot` contano come `runner`); `session.sh vram` (`nvidia-smi --query-gpu=memory.used,memory.total` e `--query-compute-apps`).
- `bash spikes/tools/hw-manifest.sh <out.json> [--image <ref>]… [--tool nome=versione]…`: aggiunge `run_id` (da `--run-id <run_id>` o `CKA_RUN_ID`), `compose_project` e `containers` (nome, servizio, immagine e image ID dei container etichettati col run_id).
- `bash spikes/tools/runner-smoke.sh <run_id>`: idempotente (inizializza i volumi con `session.sh init-volumes`); consumatori lo rilanciano se un volume del runner è stato ricreato.
- Runner: `curl`, `findutils` (xargs), `qpdf`, `poppler-utils`, `imagemagick`, `python3`, `oha`; `/work/tmp` scrivibile da 10001 con ≥ 20 GiB liberi (verificato dallo smoke). `S01_TARGET_URL` in `spikes.env` = URL del job `cka-s01-server` porta 8080 percorso `/upload` (forma solo in commento in `.env.example`).
- Pesi Docling: volume `docling-models` (sola lettura in docling e docling-cpu), manifest in `spikes/results/docling-models.txt`; parametro `DOCLING_ARTIFACTS_PATH` (default `/models`).
