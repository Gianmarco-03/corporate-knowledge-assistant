## Assegnazione dei pattern

### `spikes/s02-parser/src/bin/parse-parent.rs` (driver di misura, batch)

**Header da cambiare** (riga 56):
```rust
const OVERHEAD_HEADER: &str = "mode,concurrency,run,docs,wall_ms,spawn_init_ms,docs_per_s";
```
Diventa `...,docs_per_s,status` (D-02). `csv_writer` (851-854) costruisce le colonne dall'header e `common::csv::Writer::write_row` rifiuta una riga con un numero di campi diverso (`spikes/common/src/csv.rs:46-53`): entrambi gli array `row` di `cmd_overhead` (1231-1239 e 1257-1265) devono passare da 7 a 8 campi.

**D-01, difetto attuale di `cmd_budget`** (righe 1049-1050 e 1116):
```rust
    let input = selftest_input(run_tag)?;
    let mut w = csv_writer(out, BUDGET_HEADER)?;   // `?` esce lasciando il file
    ...
    let _ = std::fs::remove_file(&input);           // solo sul percorso riuscito
```
Dopo la creazione dell'input ci sono altri `?` che oggi lasciano il file: `budget()?` (1053), `w.write_row(&refs)?` (1114), e il `return Ok(Exit(2))` su `prepare_job` (1079). La correzione deve coprirli tutti. Nel file non esiste un pattern RAII o guard: l'unico cleanup è il `let _ = remove_file` di 1116. Due forme coerenti con lo stile del file:
- spostare il corpo dopo `selftest_input` in una `async fn` interna e fare `let r = inner(...).await; let _ = std::fs::remove_file(&input); r` (mantiene codici d'uscita e messaggi identici, come chiede D-01);
- una piccola struct guard con `impl Drop` che chiama `remove_file`, come fa il lanciatore per la cartella del job (vedi `isolate::run_child`, cleanup sul drop, verificato dal test `dropped_future_kills_group_and_cleans_within_one_second` in `tests/isolation.rs:986-1031`).

`selftest_input` (986-994) legge già `S02_WORK_ROOT` (default `/work`): è il gancio che permette al test di puntare la radice dei job su una cartella del test e di contarne il contenuto.

**D-02, difetto attuale di `cmd_overhead`** (riga 1255):
```rust
            in_process_run(&pdfium, &bytes, OVERHEAD_DOCS_PER_RUN, n)?;
```
`in_process_run` (1128-1157) appiattisce l'errore in stringa: `.map_err(|e| anyhow::anyhow!("pdfium: {e}"))?` (1142). Per classificare `error:pdfium_format` serve conservare il tipo (`pdfium_render::prelude::PdfiumError`, l'errore osservato è `PdfiumLibraryInternalError(FormatError)`), per esempio facendo restituire a `in_process_run` un `Result<(), PdfiumError>` o un piccolo enum di esito, e mappandolo in una stringa `error:<tipo>` in una funzione pura (testabile in `mod tests` come `hostile_verdict`). Il panico di un thread (`"thread in-process"`, 1153) è anch'esso un errore di ripetizione.

**Pattern da copiare per «una riga per ripetizione anche in errore»:** `cmd_hostile`, righe 896-958. L'esito del job diventa un `match` che produce sempre un `Vec<String>` di larghezza fissa; nel ramo `Err` i campi senza senso sono `String::new()` e l'errore va su stderr:
```rust
            let row: Vec<String> = match res {
                Ok(r) => { ... vec![ ...14 campi... ] }
                Err(e) => {
                    let (outcome, kind) = match job_error_of(&e) {
                        Some(je) => ("job_error", je.code.as_str().to_owned()),
                        None => {
                            eprintln!("hostile: launch_error job_id={job_id}: {e:#}");
                            ("launch_error", String::new())
                        }
                    };
                    vec![ c.case_id.clone(), run.to_string(), ..., String::new(), ... ]
                }
            };
            let refs: Vec<&str> = row.iter().map(String::as_str).collect();
            w.write_row(&refs)?;
```
Per il modo in-process in errore: `wall_ms`, `spawn_init_ms` e `docs_per_s` vuoti (D-02), `status` = `error:pdfium_format`; diagnostica su stderr col prefisso `overhead:` (stile di 1170, 1187, 1223).

**Errori fatali che restano fatali (D-02):** lettura dell'input (1245 `std::fs::read(input).with_context(...)?`), bind di PDFium (1247-1250 `map_err(... "pdfium_bind: {e}")?`), creazione e scrittura del CSV (`csv_writer(...)?` 1192, `w.write_row(&refs)?` 1241/1267). Questi `?` non si toccano.

**Modo `child-per-doc`:** già non si interrompe (1212-1225: gli `Err` vanno su stderr). Con la colonna nuova serve decidere lo `status` della riga: `ok` se tutti i 16 job hanno `ChildOutcome::Ok`, altrimenti `error:<tipo>` (decisione del planner; D-02 nomina il modo in-process, ma l'header è unico).

**Codici d'uscita** (doc comment 9-10): 0 riuscito, 2 argomenti/job non validi, 3 `oom_adj_set=false`, 1 altri errori. Un errore di ripetizione in-process non deve più dare 1. Va aggiornato il doc comment del modulo (1-12) se cambia la semantica, con firma `// Modifica:` come in `compose.yaml` della 1.3.

**Test unitari nel bin:** `#[cfg(test)] mod tests` a 1277-1378, lanciati con `cargo test -p s02-parser --bin parse-parent`. Pattern di tabella pura (`hostile_verdict`) da riusare per la funzione che mappa l'errore PDFium in `status`.

**Asserzioni su exit code e stderr** (1398-1413):

    assert_eq!(o.status.code(), Some(3), "stderr {stderr}");

**Bin dei figli:** `fake-child` copiato da `env!("CARGO_BIN_EXE_fake-child")` (79-82), `parse-child` finto come script `sh` (`PARSE_CHILD_SCRIPT`, 51-58) o vero da `env!("CARGO_BIN_EXE_parse-child")` (`real_bin_dir`, 1421-1430). Il driver `overhead` lancia job `parse`, quindi serve un `parse-child` nella cartella `S02_BIN_DIR`: lo script finto basta per il modo `child-per-doc` e lo tiene veloce.

**File dei limiti** (1306-1310, `write_limits`): `overhead` richiede `--limits` (`LimitsFile::load` vuole un profilo `default`).

**`hw.json` accanto al CSV:** `common::csv::Writer::create` chiama `common::manifest::ensure_present(dir)` (`spikes/common/src/csv.rs:20-34`, `manifest.rs:29-39`). Il JSON minimo valido è quello dei test di `csv.rs:85-91`:
```rust

```
Senza `hw.json`, `create` fallisce: è il guasto naturale per D-01.

**Iniezione del guasto, D-01 (nessun gancio nuovo necessario):** `budget --concurrency 1 --jobs 1 --reserve-fraction 0.25 --run-tag <8 car.> --out <cartella senza hw.json>/budget.csv` con `S02_WORK_ROOT` = cartella vuota del test. Sulla base: exit 1, `selftest-input-<tag>` resta (RED). Con la correzione: exit 1 invariato e cartella vuota (GREEN). Questo riproduce esattamente il caso osservato da 01-18 (`--out /dev/null`, riga 184 di RISULTATI). Nota: con `--out` in una cartella senza `hw.json` il driver fallisce prima di `budget()`, quindi le variabili di budget non servono, ma conviene passarle per non dipendere dall'ordine.

**Iniezione del guasto, D-02 (nessun gancio esistente):** in `parse-parent.rs` non c'è un hook di fault injection (né feature né variabile d'ambiente oltre a `S02_BIN_DIR`, `S02_WORK_ROOT`, `S02_RESULTS_RAW`, `S02_BUDGET_TOTAL_BYTES`, `S02_PARENT_RESERVE_BYTES`, `PDFIUM_DIR`). Opzioni per il planner:
1. **Input non PDF** (nessun codice nuovo): `overhead --input <file con byte non PDF>`. PDFium in-process dà `FormatError` su ogni ripetizione; sulla base il driver esce 1 dopo le sole righe `child-per-doc` (RED), con la correzione scrive tutte le righe in-process con `status=error:pdfium_format` ed esce 0 (GREEN). Non prova però il caso «una sola ripetizione fallisce fra ripetizioni riuscite».
2. **Variabile letta solo dal padre** sul modello di `S02_BUDGET_TOTAL_BYTES` (righe 59-62, commento «Budget fisso per i test nel runner... variabili lette solo dal padre»): es. `S02_OVERHEAD_FAIL_RUN=<run>` che fa fallire la ripetizione indicata del modo in-process. Prova esattamente D-05, ma aggiunge un gancio di test a un driver di misura: va dichiarato nel doc comment e nel piano.
3. **Funzione pura + test nel bin**: estrarre il ciclo in-process in una funzione che riceve una closure `FnMut(n, run) -> Result<Duration, PdfiumError>` e testarla in `mod tests` (stile `hostile_verdict`) con una closure che fallisce alla ripetizione k. Prova la logica senza PDFium, ma non è un test d'integrazione come chiede D-05; si può combinare con l'opzione 1.

**Analogo secondario:** `tests/oom.rs` (solo in 01-18). Pattern utili: test di container marcato `#[ignore = "solo nel container a memoria bassa di 01-18"]` (226) con il lanciatore dedicato `measure/run_oom.sh`; funzioni pure di classificazione con test non ignorati in coda (422-581). ## Pattern condivisi

### Convenzione d'errore dei driver
**Fonte:** `parse-parent.rs` 155-181 e 1167-1189.
**Si applica a:** `cmd_budget`, `cmd_overhead`.
```rust
    let levels = match parse_list(concurrency) {
        Ok(l) => l,
        Err(e) => { eprintln!("overhead: {e:#}"); return Ok(Exit(2)); }
    };
```
Argomenti non validi → `Ok(Exit(2))`; `oom_adj_set=false` → `Ok(Exit(3))` dopo aver scritto il CSV; ogni altro `Err` risale a `main` → `eprintln!("parse-parent: {e:#}")`, exit 1.

### Variabili d'ambiente lette solo dal padre (gancio dei test)
**Fonte:** `parse-parent.rs` 59-62, 319-341; `selftest_input` 986-994.
**Si applica a:** `tests/drivers.rs` e a un eventuale gancio nuovo per D-02.

### Firma e *Storia*

**Si applica a:** ogni file toccato. Nel codice Rust la firma va su un commento non doc: `// Modifica: Claude (gsd-executor 01.4-01) · <data> · <cosa>` (forma usata dalla 1.3 in `s05-cancel/src/main.rs`).
